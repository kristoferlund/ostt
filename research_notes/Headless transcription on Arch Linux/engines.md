# Reusable headless speech-to-text backends on Arch Linux

## Which projects are actually reusable backends?

### Takeaway
Shortlist **whisper.cpp, faster-whisper, sherpa-onnx, RealtimeSTT, and Wyoming Faster Whisper**. These are not five interchangeable engines: the first three implement inference; RealtimeSTT adds recording/VAD/session orchestration, and Wyoming exposes inference through a voice-assistant protocol. All offer local inference rather than requiring a hosted cloud STT account. [whisper.cpp](https://github.com/ggml-org/whisper.cpp); [faster-whisper](https://github.com/SYSTRAN/faster-whisper); [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx); [RealtimeSTT](https://github.com/KoljaB/RealtimeSTT); [Wyoming](https://github.com/OHF-Voice/wyoming-faster-whisper)

### Cited Findings

| Candidate / layer | Architecture and hardware | Streaming versus final text | Headless integration |
|---|---|---|---|
| **whisper.cpp — native inference library + example HTTP server** | C/C++ Whisper implementation; CPU, NVIDIA CUDA, cross-vendor Vulkan, and additional platform backends. Local model files; can self-host remotely. | The documented **server accepts complete uploaded audio**; do not equate its `--print-realtime` console flag with network microphone streaming. Separate `whisper-stream` is explicitly described upstream as a *naive* microphone/chunked inference example, not a native streaming acoustic model. | C API/shared library, `whisper-cli`, resident `whisper-server`; multipart `POST /inference`, optional ffmpeg conversion, `/load` for model changes. Documentation calls it “OAI-like,” not a guarantee that default routes match OpenAI's `/v1/audio/transcriptions`. [Engine/hardware](https://github.com/ggml-org/whisper.cpp); [server contract](https://github.com/ggml-org/whisper.cpp/tree/master/examples/server) |
| **faster-whisper — Python inference library over CTranslate2** | Whisper inference, CPU INT8 and NVIDIA CUDA FP16/INT8; documented GPU dependencies are CUDA 12/cuDNN 9. Choose a streaming model for incremental hypotheses; an offline Whisper/Parakeet model does not become streaming merely by putting it behind a socket. | Native APIs/CLI tools plus upstream **C++ WebSocket servers and clients**, with separate online/offline server documentation. Not a single standardized OpenAI HTTP endpoint. [Toolkit](https://github.com/k2-fsa/sherpa-onnx); [WebSocket architecture](https://k2-fsa.github.io/sherpa/onnx/websocket/index.html); [Rust API](https://k2-fsa.github.io/sherpa/onnx/rust-api/index.html) |
| **RealtimeSTT — reusable audio/session orchestration library + resident server** | Python, multiprocessing, VAD, optional wake words, selectable inference engines. It is **not an independent acoustic inference engine**. | Replaceable realtime hypotheses and authoritative final text are distinct. CPU profile processes new frames with Nemotron, then runs Parakeet once over the complete turn. | Recorder normally owns the microphone, but `use_microphone=False` + `feed_audio()` accepts application audio. Streaming audio transport is **not automatically streaming partial text**. [Service](https://github.com/OHF-Voice/wyoming-faster-whisper); [protocol](https://github.com/OHF-Voice/wyoming) |

- RealtimeSTT's supported production interface is separate from its legacy `stt-server` two-WebSocket recorder client. Documented endpoints include `GET /api/v1/live`, `/ready`, `/capabilities`, `POST /transcribe-pcm16`, and WebSocket `/api/v1/ws/transcribe` (with aliases). Production WS uses framed binary mono PCM16 at 16 kHz plus ordered control/events; it is **not** simply unframed PCM sent to an arbitrary WebSocket. Loopback is default; direct non-loopback binding requires bearer auth and TLS files. [Production guide](https://github.com/KoljaB/RealtimeSTT/blob/master/RealtimeSTT_server/PRODUCTION_SERVER.md)
- RealtimeSTT release **v1.1.2 already contains the production server/profile documentation**; these are not inferred future features from a roadmap. [Tagged README](https://github.com/KoljaB/RealtimeSTT/blob/v1.1.2/README.md)
- Wyoming's repository moved from `rhasspy` to **OHF-Voice**; older links redirect. Its Home Assistant app is a concrete downstream distribution/integration, with discovery through the Wyoming integration and configurable inference backends. [Current repository](https://github.com/OHF-Voice/wyoming-faster-whisper); [Home Assistant app documentation](https://github.com/home-assistant/addons/blob/master/whisper/DOCS.md)

### Inferences
- For a caller that already records audio, inference-only servers avoid competing microphone ownership. RealtimeSTT is reusable precisely because it offers external audio ingestion; its recording/VAD features need not be adopted wholesale. This is an architectural inference from the documented interfaces above.
- No desktop dictation UI deserves inclusion merely because its source code imports one of these engines. A stable external audio/transcription interface is the useful boundary; the shortlist above already supplies it without hotkey, compositor or clipboard coupling.

### Gaps
- No runtime latency, accuracy, Swedish quality or GPU benchmark was performed. Cross-project README benchmark tables use different models/options/hardware and are not a sound ranking for OSTT.
- No common stdin/stdout daemon protocol was verified. CLI/file input, native/Python APIs, HTTP, WebSocket and Wyoming TCP are the established integration paths documented above; do not advertise all five as drop-in Unix filters.
- Exact partial-transcript behavior of each current Wyoming backend was not tested. Protocol support alone does not prove a particular backend advertises it.

### Inferences
- Downloads demonstrate package/artifact retrieval, not successful transcription, retention, satisfaction or Linux desktop adoption; CI, dependency installs, repeated downloads and multiple platform assets inflate totals. Cross-layer counts must not be added to estimate users.
- `pushed_at` demonstrates repository activity, not necessarily a shipped feature or a substantive human-authored engine change. Release dates and documented downstream use are included separately to avoid that conflation.
- Wyoming is a useful counterexample to “few stars means no adoption”: integration into a distributed voice platform makes it relevant, while not establishing how many people run that particular backend.

### Gaps
- No defensible unique-active-user or Arch/Omarchy-specific install counts were found. PyPI Stats “last_month” is the API's recent-download window; the response did not supply explicit start/end dates.
- No comparable unique contributor totals were established; anonymous identities/bots and GitHub aggregation make simplistic contributor-page counts misleading.

## What is practical on Arch, and what should OSTT reuse?

### Takeaway
For a minimal resident final-transcript backend, start evaluation with **Arch's packaged whisper-server**. For true incremental recognition, **sherpa-onnx** is the most direct inference-level option; **RealtimeSTT** supplies more complete session/VAD/server orchestration at the cost of a larger Python stack. **Wyoming** is the existing voice-assistant interoperability option. These are design recommendations, not measured performance rankings.

### Inferences
- **Smallest backend experiment:** keep OSTT's recording/provider/output responsibilities; send completed audio to a persistent loopback `whisper-server`. This tests the value of keeping weights resident without simultaneously redesigning recording and partial-text UX.
- **Streaming experiment:** compare native sherpa-onnx online recognition with RealtimeSTT's live/final orchestration. Define partial replacement, explicit finalization, cancellation, concurrency and model lifecycle before choosing a transport; WebSocket by itself solves none of those semantics.
- **Python/GPU service:** faster-whisper is a solid underlying inference choice, but adopting it alone means also owning server/resource/error contracts. RealtimeSTT or an existing wrapper can reduce that work; Wyoming is preferable when Wyoming interoperability is itself a goal.
- Nothing here requires a desktop UI or Omarchy-specific resident microphone daemon. Keep systemd service packaging distinct from inference capabilities and dictation frontend behavior.

### Gaps
- Packages were inspected via metadata/manifests, **not installed or built**. AUR PKGBUILD scraping hit Anubis, so exact AUR build options, service units and optional server binaries remain unverified.
- No promise is made that upstream CLI stdout is machine-clean or that all flags/options match across Arch/AUR/upstream versions. Validate the selected version's contract in an actual integration test.
