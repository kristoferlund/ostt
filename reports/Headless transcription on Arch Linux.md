# Choose engines, not just dictation daemons

**Research date: October 21, 2026.**

**Voxtype offers reusable headless transcription components, but not a ready-made general-purpose resident transcription service.** Its public Rust API accepts audio buffers; its CLI transcribes WAV files without the dictation daemon. Its resident daemon primarily controls microphone dictation, rather than accepting arbitrary client audio. For that service boundary, evaluate **whisper.cpp’s HTTP server**, **sherpa-onnx’s WebSocket servers**, or a higher-level service such as **RealtimeSTT**. Omarchy officially integrates external dictation tools, not an Omarchy-owned recognition engine: stable **4.0.6 remains opt-in Voxtype**, while **4.5.0-rc1 introduces Superwhisper as the fresh-install default**. The earlier sketch is unavailable, so equivalence must remain conditional. ([Voxtype API](https://github.com/peteonrails/voxtype/blob/dc499ad47444ba6ea80d8750aa3581c23120821c/src/transcribe/mod.rs), [stable manual](https://github.com/omacom/omarchy/blob/v4.0.6/manual/11-text-extraction-dictation.md), [RC release](https://github.com/omacom/omarchy/releases/tag/v4.5.0-rc1))

## Voxtype separates inference, but not as a shared service

The inspected Voxtype v1.1.1 source exposes `Transcriber::transcribe(&self, samples: &[f32])` for **16 kHz mono audio**, a factory, and an in-process streaming abstraction. Another Rust application can supply audio without invoking hotkeys, capture or desktop output. Keeping a transcriber instance retains its model context. However, these interfaces live inside the main application package, not a separately packaged lean engine crate, and the research established no stable external SDK guarantee. ([Public API](https://github.com/peteonrails/voxtype/blob/dc499ad47444ba6ea80d8750aa3581c23120821c/src/transcribe/mod.rs#L101-L163), [package](https://github.com/peteonrails/voxtype/blob/dc499ad47444ba6ea80d8750aa3581c23120821c/Cargo.toml))

`voxtype transcribe recording.wav` is useful batch integration, but **creates a fresh transcriber and exits**; it does not reuse the daemon’s warm model. Its implementation reads WAV, not arbitrary MP3/Opus, and mixes progress messages with transcript stdout. The hidden stdin `transcribe-worker` is Whisper-only, handles one request, and exists for internal GPU isolation—not a supported persistent protocol. ([File implementation](https://github.com/peteonrails/voxtype/blob/dc499ad47444ba6ea80d8750aa3581c23120821c/src/app/transcribe_file.rs), [worker](https://github.com/peteonrails/voxtype/blob/dc499ad47444ba6ea80d8750aa3581c23120821c/src/transcribe/worker.rs))

For a custom dictation frontend, `record start --file=out.txt --no-osd` and `record stop --wait --json` provide useful controls. But they control **Voxtype’s microphone**, not caller-supplied audio. The inspected Unix socket broadcasts waveform metrics, and its remote HTTP backend is a client—not an exposed transcription server. Thus “no window,” “embeddable inference,” and “shared audio→text service” are distinct capabilities. ([Recording interface](https://github.com/peteonrails/voxtype/blob/dc499ad47444ba6ea80d8750aa3581c23120821c/src/cli/record.rs), [socket purpose](https://github.com/peteonrails/voxtype/blob/dc499ad47444ba6ea80d8750aa3581c23120821c/src/audio/levels.rs), [remote client](https://github.com/peteonrails/voxtype/blob/dc499ad47444ba6ea80d8750aa3581c23120821c/src/transcribe/remote.rs))

## Existing backends cover batch, streaming and orchestration

**whisper.cpp is the simplest packaged service baseline on Arch.** Official Extra’s `whisper-cpp` includes `whisper-server`, `whisper-cli` and `libwhisper.so`. The resident server accepts uploaded audio through `POST /inference`; its documented contract is “OAI-like,” not necessarily OpenAI’s standard route. It suits completed recordings. Neither console realtime printing nor the separate microphone example establishes genuine incremental network recognition. The example server also carries an upstream sandbox/non-root warning. ([Arch manifest](https://archlinux.org/packages/extra/x86_64/whisper-cpp/files/), [server contract](https://github.com/ggml-org/whisper.cpp/tree/master/examples/server))

**faster-whisper is an inference library, not a first-party daemon.** Its Python API supports CPU INT8 and NVIDIA CUDA; retaining `WhisperModel` permits resident inference. A segment generator is not a live-streaming protocol. Existing wrappers such as Speaches add a service boundary, while WhisperX demonstrates downstream reuse. Choose this route for Python/CUDA integration, accounting for CTranslate2, CUDA and cuDNN compatibility. ([Upstream usage and integrations](https://github.com/SYSTRAN/faster-whisper))

**sherpa-onnx is the clearest inference-level candidate for genuine streaming.** It offers native/binding APIs and separate online/offline WebSocket servers. Model selection matters: an offline model behind a socket does not become streaming. **RealtimeSTT** instead adds VAD/session orchestration, external `feed_audio()` input, and a documented resident production HTTP/WebSocket service; it is not an independent acoustic engine. Its v1.1.2 documentation includes that service, with Python 3.11/3.12 release targets rather than assumed compatibility with Arch’s current system Python. ([sherpa servers](https://k2-fsa.github.io/sherpa/onnx/websocket/index.html), [RealtimeSTT tagged documentation](https://github.com/KoljaB/RealtimeSTT/tree/v1.1.2))

**Wyoming Faster Whisper** provides a resident audio→text service with concrete Home Assistant integration. It uses Wyoming TCP events and binary audio, not HTTP/OpenAI. Streaming audio transport does not guarantee partial transcripts; verify the selected backend’s capabilities. Choose it when voice-assistant interoperability matters. ([Service](https://github.com/OHF-Voice/wyoming-faster-whisper), [Home Assistant integration](https://github.com/home-assistant/addons/blob/master/whisper/DOCS.md))

## Maintenance and distribution establish reuse, not user counts

The notes record October 2026 repository activity for all five candidates. Recent releases include whisper.cpp **1.9.5**, sherpa-onnx **1.13.8**, RealtimeSTT **1.1.2**, and Wyoming **3.8.1**. Faster-whisper’s **1.2.1** release is older, but the observed repository activity and named integrations argue against calling it abandoned. ([Releases/activity](https://github.com/ggml-org/whisper.cpp/releases), [sherpa releases](https://github.com/k2-fsa/sherpa-onnx/releases), [RealtimeSTT release](https://github.com/KoljaB/RealtimeSTT/releases/tag/v1.1.2), [Wyoming release](https://github.com/OHF-Voice/wyoming-faster-whisper/releases/tag/v3.8.1), [faster-whisper metadata](https://api.github.com/repos/SYSTRAN/faster-whisper))

Arch packaging, documented downstream integrations and Omarchy user/upstream bug collaboration establish real distribution and use. **Stars, forks, package downloads and AUR votes are adoption proxies—not active users or Arch/Omarchy market share.** Faster-whisper and sherpa-onnx have AUR packages; the observed Wyoming AUR package lags upstream. Package availability does not verify optional server binaries or GPU build flags. ([faster-whisper AUR](https://aur.archlinux.org/packages/python-faster-whisper), [sherpa AUR](https://aur.archlinux.org/packages/sherpa-onnx), [Wyoming AUR](https://aur.archlinux.org/packages/python-wyoming-faster-whisper), [Omarchy/upstream feedback](https://github.com/omacom/omarchy/issues/4159))

## Omarchy ships dictation integration, with a release-channel split

Official stable support began with **3.3.0’s opt-in Voxtype integration**. Latest stable **4.0.6**, published October 19, still directs installation through **Install → AI → Dictation**. Official integration therefore does not mean installed by default. ([Initial release](https://github.com/omacom/omarchy/releases/tag/v3.3.0), [stable installer](https://github.com/omacom/omarchy/blob/v4.0.6/bin/omarchy-voxtype-install))

DHH’s merged changes add selectable providers and a common dictation interface, then make **Superwhisper with cloud-processing defaults** the fresh-install choice. These are included in **4.5.0-rc1**, released October 20—not latest stable. Existing provider choices are preserved. The live manual describes this newer workflow; tagged stable source is authoritative for stable claims. Provider adapters are desktop orchestration, not a general audio-submission API or new recognition engine. ([Provider PR](https://github.com/omacom/omarchy/pull/14552), [default-change PR](https://github.com/omacom/omarchy/pull/14625), [RC release](https://github.com/omacom/omarchy/releases/tag/v4.5.0-rc1))

Proposed Cohere/Vulkan defaults, Intel NPU support and speaker-audio transcription remained unmerged at the cutoff. No official Handy integration or Omarchy-owned headless transcription service was established. Installation reliability, acceleration, latency, accuracy and display-independent operation were **not runtime-tested**; declared defaults are not proof of flawless first-run behavior. ([Cohere proposal](https://github.com/omacom/omarchy/pull/13098), [NPU proposal](https://github.com/omacom/omarchy/pull/5177), [speaker proposal](https://github.com/omacom/omarchy/pull/15282), [first-run report](https://github.com/omacom/omarchy/issues/15551))

## Conclusion

If the missing sketch meant “several clients submit audio to one warm engine,” local OSTT evidence is closer: its inspected daemon already accepts **audio-file paths over a Unix socket** and retains a model. That is not streamed audio, nor proof of the earlier conversation. Evaluate replacement engines against that existing boundary before adding another daemon. Use Voxtype for Rust embedding or dictation control; benchmark whisper-server for final-text service reuse, and sherpa-onnx/RealtimeSTT only if incremental text is a requirement. ([OSTT daemon](https://github.com/kristoferlund/ostt/blob/1bd84b89210d99a9f14353254462044872362f6f/src/transcription/daemon.rs))
